Fretboard Visualizer: a code tour

A stateless Go server works out guitar chord shapes; a plain-JavaScript page draws them. This tour goes from the outside in: the big picture, one click followed through every layer, the file map, then the Go idioms the code leans on, and the few places it bends them.

1,487 lines of Go in 11 files1,908 lines of Go tests707 lines of JavaScript0 dependenciesGo 1.25.5

Every code block is quoted from the real source, with its file name. This is a snapshot from September 24, 2026. Function names are the handle; line numbers are left out because they move.

1The big picture

A guitar chord is a set of notes; a shape is one way of playing them on six strings. The server finds every playable shape for a chord in a given tuning, and the page shows one at a time.

Four rules the code follows

  1. The server is stateless. Every request carries everything it needs (root, quality, inversion, tuning…). The browser keeps the chord, tuning and progression in memory. Nothing is saved.
  2. All music logic lives in music/ and guitar/. music/ is instrument-independent theory and guitar/ builds on it. api.go only translates HTTP ⇄ those types, and the JavaScript never spells a chord or decides a fingering. It draws what it is given.
  3. One binary. Deploying means copying one file, because the frontend is embedded.
  4. Standard library only. go.mod has no require lines. net/http, encoding/json, embed, slices and cmp cover everything.

2Follow one click

C major is showing, its first shape is xxx010, and you click the B string at fret 8. Every step below is real code from that path. Use the buttons or the ← → keys.

Step 1 of 9

The click lands on an invisible target

web/js/fretboard.js

renderFretboard draws 6 × 23 transparent rectangles, one per string and fret. Each click handler closes over its own s and f and calls onPick, a function main.js passed in. fretboard.js never touches app state: it rebuilds the SVG from whatever it is given.

Step 2 of 9

main.js decides what to ask

web/js/main.js

pickSpot pauses playback (the spec says every explorer control does), then asks for shapes with at=string:fret. If a progression step is loaded, the newly chosen shape is copied into that step, exactly like the ◀ ▶ buttons do.

Step 3 of 9

One function talks to the server, and ignores stale answers

web/js/main.js

loadVoicings takes a ticket with ++seq. When the response arrives, my !== seq drops it if a newer request has started, so a slow answer can never overwrite a fresh one. Then it stores the chord, the shapes and which shape is current.

Step 4 of 9

api.js turns options into a URL

web/js/api.js

URLSearchParams handles the escaping (that is why ♯ and commas are safe) and empty values are skipped. A non-2xx response becomes a thrown Error carrying the server's message.

Step 5 of 9

Go routes it

api.go

A ServeMux pattern can include the HTTP method (Go 1.22). "GET /api/voicings" only matches GET, so a POST there gets a 405 for free. The last line serves the embedded frontend for everything else.

Step 6 of 9

The handler validates, then hands off to music and guitar

api.go

Every parameter is checked before any work happens, and each failure becomes a 400 whose message starts with the parameter name. Optional inputs are pointers: near and at stay nil when absent. Then generate builds the shapes and NearestIndexAt picks one.

Go idioms here: 1 · errors are values 4 · values & pointers 11 · DTOs

Step 7 of 9

guitar searches every fingering

guitar/guitar_voicing_generator.go

A depth-first walk over the six strings. Each string may be muted, or fretted at any fret whose pitch class is a chord tone. A branch is abandoned as soon as its fret span exceeds 3. At each leaf the shape must contain every required tone (one bitmask comparison), be playable, respect the inversion and the open-string limit. Even the largest chord (Cmaj13) takes about 3 ms; the version before this one took about 7 s.

Go idioms here: 9 · modern stdlib 10 · closures

Step 8 of 9

…and picks the nearest one

guitar/nearest.go

Among shapes that play exactly the clicked spot, NearestIndex chooses the one with the least finger movement from the current shape. If no shape plays it (a non-chord tone), closestToFret falls back to the shape whose fret range is nearest the click.

Go idioms here: 4 · values & pointers

Step 9 of 9

JSON comes back and the page redraws

web/js/main.js

The response carries the chord's tones, the chosen shape (frets and tones run low→high), nearestIndex, and fretboard, a map of every chord tone on the neck (used by the “All chord tones” toggle). main.js stores it in state and calls render(), which rebuilds the SVG from scratch.

4The music and guitar packages

Pure logic with no net/http and no encoding/json. You can test all of it without starting a server. music holds the instrument-independent theory; guitar imports it and never the other way round, so another instrument could sit beside guitar. Each layer below depends only on the layers under it.

  1. 5 · Search & chooseguitar/ · guitar_voicing_generator.go · nearest.go

    Find every playable shape, sort them, pick the nearest to a reference.

  2. 4 · Voicingsguitar/ · guitar_voicing.go

    A chord played on a tuning: the playability rules, “does this shape contain the chord?”, which note is lowest.

  3. 3 · Guitar foundationsguitar/ · tuning.go · fingering.go · fretboard.go

    Tunings, the x32010 notation, and which chord tone sounds at each string and fret.

  4. 2 · Chordsmusic/ · chord.go · inversion.go · diatonic.go

    Qualities as data, spelling, required tones, inversions, modes and diatonic chords.

  5. 1 · Foundationsmusic/ · note.go

    Notes, accidentals, pitch classes and absolute pitch.

Two ways to number a note

SemitoneValue() is the pitch class (0–11): it answers “is this note in the chord?”. MIDI() is the absolute pitch: it answers “which string sounds lowest?”, which matters because strings can cross in pitch (a high fret on a low string can sound above an open string next to it). Accidental is a signed count, so double sharps and flats (F♯♯, B♭♭) spell correctly.

Strings are stored high→low; the wire speaks low→high

Inside guitar, Fingering[0] is the high e (inherited from the original app). The API and the UI count from the low string. The flip happens only at the edges: fingering.go, tuning.go and api.go, each with round-trip tests. Whenever you touch a string index, ask yourself which order you are in.

Chord qualities are data, not code

Adding a chord type means adding one row to qualityTable: an id, a label, a suffix, and its tones (a degree, a size in semitones, and whether it may be omitted). Spelling, interval labels, required tones and the inversions offered all come from that table. Spell derives the note letter from the degree, so B♭ major is B♭ D F and never A♯ D F.

“Required tone” is a bitmask comparison

Each chord becomes two 12-bit masks, one bit per pitch class: every chord tone, and the required ones. A shape matches when every sounded pitch class is in the chord and every required one is present. Both tests are single integer operations.

Ties are decided with integers, not floats

When two shapes need the same finger movement, the nearer average fret wins. Comparing averages as float64 lets rounding noise decide a true tie, so the code cross-multiplies the fractions instead (dist*bestN against bestDist*n) and only then falls through to the next rule.

5The HTTP layer

Package main is thin on purpose: parse, validate, call music and guitar, encode.

main.go

The whole entry point. webFS is filled at compile time; fs.Sub makes / serve web/index.html. Because the files are baked in, edit web/ → restart the server.

Errors: one shape, made in one place

Every validation failure is an ordinary error, wrapped with the parameter name (%w), and the handler turns it into 400 {"error": "openMax: want an integer from 0 to 22, got \"x\""}. parseInt rejects +5 and 05 on purpose, so each value has exactly one spelling.

Optional JSON fields are pointers

OpenMax *int is nil when the client leaves it out, which is different from an explicit 0 (a legal value meaning “open strings only when nothing is fretted”). handleProgression also caps the request body with http.MaxBytesReader.

6The frontend

Small on purpose: about 700 lines across five modules.

There is no framework and no build step: index.html loads main.js with <script type="module">, and the modules import each other. The pattern is state → render(): events change state and call render(), which rebuilds the controls and the SVG from it. renderFretboard is pure (same input, same drawing) and reports clicks back through a callback.

The seq ticket you saw in step 3 is the frontend’s one concurrency rule: the latest request wins. settingSeq applies the same rule to tuning and open-string changes, which recalculate every step: a superseded answer is dropped, and shapes are written to the step objects that were sent rather than to list positions.

7Go idioms in use

Eleven patterns you will meet in almost any Go codebase, each with the place it appears here.

1

Errors are values, wrapped with context

everywhere in Go

Go has no exceptions. A function that can fail returns an error as its last value and the caller decides what to do. music.ParseNote returns (Note, error); api.go wraps that with the parameter name using %w; only the handler decides the consequence (an HTTP 400). Guard clauses return early so the happy path stays un-indented. errRequired is a sentinel: a package-level error value callers can compare against (we do not use errors.Is yet, but %w keeps that open).

2

Capital letter = exported

package design

Capitalised names are visible to other packages; lowercase names are private to their own. That is the whole access-control system. go doc ./music and go doc ./guitar show what api.go can use. Helpers such as opensPastFret and fretDistance are invisible to it, yet the tests can call them because the tests are also in package guitar.

3

Enums are named ints plus iota

everywhere in Go

Go has no enum keyword. The idiom is a named integer type, a const block using iota, and a String() method so fmt prints names. Inversion, ChordQuality and Mode all follow it. Indexing an array by the enum (inversionNames[i], qualityTable[q]) keeps the names and data next to the constants.

4

Arrays are values; pointers mean “maybe absent”

a Go surprise

[6]int is an array, a value: assigning or passing one copies it, and two arrays are comparable with ==. The tests compare whole fingerings with got != want. Tuning (a struct holding [6]Note) is comparable too. Go has no optional parameters and no null, so “might not be there” is a pointer: near *[6]int is nil when the URL has no near, and NearestIndexAt(…, current *[6]int, …) reads the same way.

5

Accept interfaces, return concrete types

API design

Ask for the smallest interface you need. newMux takes an fs.FS (an interface with one method) instead of the concrete embed.FS, so it works with the embedded files, a directory (os.DirFS) or an in-memory fstest.MapFS. It returns the concrete *http.ServeMux.

6

embed and the modern ServeMux

Go 1.16 · 1.22

//go:embed web makes webFS hold the frontend at compile time: one file to deploy. Since Go 1.22 a ServeMux pattern can include the method ("GET /api/voicings"), replacing hand-written if r.Method != … checks; other methods get a 405 automatically, which this test proves.

7

Table-driven tests, helpers that say t.Helper()

testing

Tests are ordinary functions (TestXxx(t *testing.T)) in _test.go files. The idiom is a slice of cases and a loop: adding a case is one line, and a failure names the case. Helpers call t.Helper() so a failure points at the caller’s line, not the helper’s.

8

Test the clever code against something obviously right

testing

The generator is clever (a pruned search over bitmasks), so a test compares it with something slow and obviously correct: bruteForce tries every fingering {x, 0…22}⁶ (with a fret-span cut-off so it finishes) and filters with the same public checks. Any disagreement is a bug in the clever one. The benchmark uses for b.Loop() (Go 1.24) and runs with go test -bench.

9

The modern standard library replaced a lot of boilerplate

Go 1.21 · 1.22

slices.SortFunc with cmp.Compare (1.21) instead of sort.Slice index juggling; built-in min and max (1.21); for i := range 6 (1.22) instead of for i := 0; i < 6; i++. Older-style loops survive in inherited code: CalculateFingerMovement still has one.

10

Closures let a recursive search share state

everywhere in Go

A function literal can capture variables from where it is written. The search declares var walk func(…) first so the literal can call itself, then shares fingering, voicings, candidates and required with every recursive call, with no struct and no extra parameters.

11

Wire types are separate from domain types

API design

The types that model music (Note, Chord, GuitarChordVoicing) carry no JSON tags. The wire format lives in separate …JSON structs in api.go, built by small constructors like newChordJSON and newVoicingJSON. The API can change without touching music/, and the other way round. Note NearestIndex *int with omitempty: a pointer tells “absent” apart from a real 0.

8Where it bends the rules

Honest notes, so you do not learn a habit that is not one. Some of these came with the original code; some are mine.

  • Get prefixes

    Go style drops them: a method for a value is just its name (MinFret(), not GetMinFret()). GetMinFret and GetAverageFretPosition come from the original app. GetAverageFretPosition is no longer called anywhere, so it is dead code, left alone on purpose.

  • float64 for a whole number

    CalculateFingerMovement returns a float64, but the movement is always an integer. The signature is inherited; an int would be more natural and would make the exact-tie logic more obviously exact.

  • A bare ListenAndServe

    Fine on your laptop. For the public internet you would build an http.Server{ReadHeaderTimeout: …} with timeouts and shut it down gracefully with Shutdown(ctx). The address is hard-coded too.

  • An ignored error

    writeJSON drops the error from Encode. That is common (the headers are usually already sent by then), but linters such as errcheck flag it; at least log it.

  • Handlers are plain functions

    While the server is stateless that is the simplest thing. The moment it needs configuration (limits, defaults, a logger), a type server struct{…} with handler methods is the idiomatic home for it.

  • Value vs pointer receivers

    Chord, Note and ChordQuality use value receivers (small, immutable). GuitarChordVoicing uses pointer receivers even though its methods only read. Each type is consistent, which is the real rule, but it means you need an addressable variable to call them, hence this line in NearestIndex:

  • No automated frontend tests

    The Go side has tests; the browser side was checked with throwaway scripts kept outside the repo.
